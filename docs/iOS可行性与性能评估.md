# Fancam Duck iOS 可行性与性能评估

日期：2026年10月17日  
评估对象：产品与技术方案1.1，YOLO26s-pose、TrackTrack、OSNet x0.25  
评估性质：官方能力核查、架构复核与计算预算分析，不是真机测试报告

## 评估结论

该方案具有实现iOS本机离线产品的技术基础，可以继续原型设计，并进入有限范围的技术验证。暂不具备承诺A15实时分析、同服装遮挡后高成功率自动恢复或700MB峰值内存的证据。

最需要调整的是执行流程：全源逐帧Pose扫描、选人后二次解码提取外观、倒序读取和局部重检可能叠加成为主要成本。身份准确性的主要风险是相似服装、转身、低清和遮挡造成的信息不足；TrackTrack的公开结果不能直接代表更换检测器和ReID后的组合。

建议保持三个核心组件，先优化数据经过它们的顺序。将原方案的60秒、90秒和700MB视为待验证目标，不作为已具备能力。

## 依据与当前验证范围

已核查官方Core ML部署文档、TrackTrack参考实现、OSNet结构与模型库、Apple性能分析和后台任务资料。本地存在Xcode 27.1。当前项目只有设计文档，没有应用工程、导出模型或已执行的设备基准，因此本报告不提供伪装成实测的机型延迟。

Ultralytics官方提供YOLO26 Pose的Core ML导出。其公开iPhone速度表使用YOLO26n INT8、iPhone 17 Pro、单图短时间测试；其中Pose为约3.9ms。这个数字只证明对应配置可在设备上执行，不能替代YOLO26s-pose FP16在A15或A17 Pro上的持续处理测试。[Core ML导出与测试条件](https://docs.ultralytics.com/integrations/coreml)

## 模块可行性

| 模块 | 可行性判断 | 首要验证 |
| --- | --- | --- |
| 视频导入与时间轴 | 高，使用系统媒体能力 | iCloud、旋转、可变帧率、HDR与轨道偏移 |
| YOLO26s-pose | 有官方部署路径，具体性能未定 | 精确权重和输出方式、转换误差、算子分配与持续推理 |
| TrackTrack | 关联逻辑可移植，需要工程工作 | 与固定参考实现的一致性、采样间隔、运动相机 |
| OSNet x0.25 | 架构适合尝试端侧转换，尚未验证导出 | 推理分支、归一化、分组卷积执行与候选排序 |
| 手动框选和局部重检 | 可实现，适合修复部分小人物漏检 | 坐标还原、多人候选、连续漏检和重检预算 |
| 身份恢复 | 有条件可行，是最大效果风险 | 同服装、完全遮挡、背身、远景 |
| 平滑运镜 | 计算规模可控，观感需要迭代 | 身体保护与平滑约束冲突 |
| 竖屏预览与导出 | 有成熟系统组件 | 缓冲与GPU带宽、色彩、音画同步 |
| 后台持续处理 | 依系统版本与设备能力，不能普遍保证 | 后台资源支持、任务取消、检查点恢复 |

### YOLO26s-pose

固定640输入有利于建立可复现的性能基线。全画面一次推理输出全部人物，网络主干工作量不会因为从2人变为10人就简单变成5倍；人数增加主要加大关联、外观提取和后处理工作。

640输入也限制识别信息。1920宽的原画面缩至640后，一个原始高度120像素的舞者仅约40像素高，手腕和脚踝会更难定位。4K画面中高度200像素的人缩至640宽后仅约33像素高。更高源分辨率不自动提升固定640全图模型看到的人物细节。

应确认关键输出确实适合跟踪：候选数量、置信度分布、边缘人物、重叠人物和关键点有效性。转换成功不等于人物检测结果与原模型完全一致。

计算单元先比较CPU加Neural Engine与允许全部计算单元两种配置。分析页和预览页可以采用不同调度，但必须实测；不能认定允许GPU就必然更快，也不能把ANE理论算力直接换算成帧率。

### TrackTrack

参考仓库使用YOLOX和FastReID组成实验流水线。换成YOLO26s-pose和OSNet后，需要重新校准匹配阈值和特征分布，不能直接继承论文指标。[作者参考实现](https://github.com/kamkyu94/TrackTrack)

首版人数有限，关联数学计算预计不是主耗时；这是一项工程推断，必须测量包含丢失轨迹和候选数量后的真实耗时。无需在iOS运行Python；可以用Swift或C++实现必要状态和矩阵操作。

选择作者版或Ultralytics集成版中的一个作为固定参考，避免混用两者。稀疏外观、可变时间步长、人工否决关联和倒序分析属于需要单独验证的应用改动。缺少外观特征应表示未知，不能用零向量代表不相似。[集成实现接口](https://docs.ultralytics.com/reference/trackers/track_tracker)

移动机位还需要相机运动处理。若选用实现包含全局运动补偿，就验证其低分辨率背景估计和运动人物排除；若未实现，先把明显平移、摇摄或变焦列为单独风险，不隐藏在普通素材平均结果中。

### OSNet

官方模型库给出的x0.25规模约0.2M参数、0.08GFLOPs，输入高256宽128；这是模型复杂度，不是iPhone耗时。[OSNet模型库](https://github.com/KaiyangZhou/deep-person-reid/blob/master/docs/MODEL_ZOO.md)

结构包含常规卷积、分组卷积、池化与门控等操作，存在Core ML转换的合理基础，但仍需要实际导出确认。必须导出评估模式下的特征分支，而非人物类别分类输出；固定RGB顺序、裁切方式、训练时均值方差、输出维度及L2归一化。[模型结构](https://github.com/KaiyangZhou/deep-person-reid/blob/master/torchreid/models/osnet.py)

相同服装、低清背身和遮挡后混合裁块可能使正负候选特征重叠。增加特征库数量或提高接受阈值不能凭空恢复身份信息，反而可能增加误拒绝或污染。应按正面到背面、同服装不同人、无遮挡到部分遮挡分别绘制匹配分布，检查错误接受与正确覆盖的取舍。

## 处理流程与性能风险

### 自动首末人物帧

逐帧执行模型不能保证检测真值，但有助于排除抽帧漏掉短暂出现的情况。自动范围应继续表达为可靠检测边界，允许人工覆盖。

为了找第一与最后人物帧，不必预先分析中间所有帧。建议从开头顺序查找首个可靠人物，从结尾按可解码块反向查找最后人物。在块内按帧检查边界并复核，首次、末次事件得到确认后停止对应方向扫描。共享已检查区间，避免无人视频被重复扫描两遍。

该方法保留边界搜索的帧覆盖要求，但尾部读取受压缩视频关键帧和读取实现影响。长空白片头片尾、全程无人仍是最坏情况。快速抽帧可以给临时建议，不能替代对尚未覆盖边缘区间的确认。

场景影响很大：10分钟源视频截取30秒，若整源30 fps逐帧跑Pose，共18000次；假设每次25ms，仅Pose累计450秒。选段30秒只有900次，累计22.5秒。两者相差主要来自处理范围，与是否优化TrackTrack无关。这是算术情景，不是设备预测。

### 避免默认第二遍全量解码

选人后，尽量在选段顺序解码的原帧仍可用时完成Pose、关联需求判断及必要ReID，再释放原帧。已经有全图观测的帧可跳过Pose，但读取原像素仍计成本。

导入期间缓存人物观测和少量候选缩略图，不为所有帧、所有人保存高分辨率图像。若用户选择目标时相关帧已释放，可以按区间重读，密集请求合并顺序处理。保留有限二次解码能力，不要求完全消除二次解码。

OSNet按目标和竞争候选调用，但需要保留足够的周围人物外观上下文。完全只在丢失后才首次提取竞争人的特征可能太迟。具体抽取策略与参考TrackTrack全外观方案做精度和速度对照。

### 倒序分析

元数据可以低成本倒序读取，压缩视频像素通常仍需按可解码区间组织读取。不能把整个前半段原始画面保留在内存里。可按小块正向解码并对块内需要的像素做有界缓存，或先顺序提取必要外观再倒序关联。

倒序只是分析时钟方向变化，并非保证与正向结果等价。边界初始化、速度状态、遮挡规则和人工锚点都需验证。首版原型可支持中间选人，技术验证必须覆盖该路径的额外耗时和峰值内存。[AVAssetReader能力](https://developer.apple.com/documentation/avfoundation/avassetreader)

### 手动框选

局部重检让小人物在640输入中占更多像素，因此对全图缩小造成的漏检有帮助。原始模糊、完全遮挡或框选包含两名重叠舞者时仍可能失败。

一次恢复先运行一次局部Pose，再对有效候选运行ReID，并做短区间重算。持续每帧全图加一次局部Pose时，Pose工作量可能接近翻倍；不能将局部区域小误认为固定640网络推理自动更便宜。应限制连续重检窗口和总调用数量，超预算或仍失败时提示换帧与人工纠正。

框选自身不产生骨骼，不提供后续无检测帧的可靠连续跟踪。不能将TrackTrack包装为仅凭手画框就可任意持续追踪的单目标跟踪器。

## 耗时预算与敏感性

将用户等待分开记录为：本地媒体准备、边界扫描、目标分析、运镜生成、预览准备、导出。网络下载另计，导入后提前计算也单独显示总成本。

保守串行预算为：

分析耗时 ≈ Pose调用次数×Pose平均耗时 + ReID人物裁块数×单裁块平均耗时 + 解码与预后处理 + 关联与落盘 + 运镜生成。

局部重检和未复用的粗扫描都计入Pose调用次数；正反任务、边界外扫描和重复读取也计入。并行流水线可能降低总时间，但共享内存带宽、GPU和热约束会限制收益。对完成任务的耗时直接统计P50与P95，不能把单帧P95乘帧数当作任务P95。

### Pose敏感性

下表是假设延迟下的累计推理时间，不是任何iPhone的预计成绩，也未包含其他处理。

| 假设每次Pose耗时 | 60秒30 fps的1800次调用 | 60秒60 fps的3600次调用 |
| --- | --- | --- |
| 15ms | 27秒 | 54秒 |
| 25ms | 45秒 | 90秒 |
| 40ms | 72秒 | 144秒 |
| 60ms | 108秒 | 216秒 |

60秒30 fps任务若要求总计60秒，假设其他阶段消耗15秒，则1800次Pose平均只能使用25ms；局部重检还会进一步压缩预算。若总计90秒，假设其他阶段20秒，对应约38.9ms。60 fps逐帧执行下，相同预算约减半。

这说明A15一分钟内预览可作为挑战目标，但必须由持续Pose延迟与完整任务共同证明。若Pose平均40ms，单Pose已超过60秒，优化小规模关联无法补回差距。

### ReID敏感性

每视频秒提取10个人物裁块，60秒共600次；假设单裁块含预处理和推理为3ms，累计1.8秒。若10人每秒30次全部提取，共18000次，同假设下为54秒。数字只用于比较调度方式，不是OSNet实测。

小模型不代表批量调用免费。需要记录实际调用数、裁切与归一化、模型调度以及密集片段中的峰值。优先验证batch 1，批处理是否收益再由固定形状和设备测试决定。

### 局部重检敏感性

以60秒30 fps视频为例，额外对10%的帧执行局部Pose，增加180次调用；假设25ms即增加4.5秒。每帧额外一次则增加45秒。可接受的自动恢复预算应从这类任务级数据确定。

## 内存与存储评估

未压缩像素是主要可控风险。以下按十进制MB计算，不含对齐、解码器内部表面和额外图像副本：

| 缓冲格式 | 1920×1080单帧 | 3840×2160单帧 |
| --- | --- | --- |
| 8位YUV420 | 约3.11MB | 约12.44MB |
| BGRA | 约8.29MB | 约33.18MB |

缓存1秒4K30 BGRA约995MB，已超过700MB目标。4K60成本更高。10位HDR的内存不能套用8位YUV420数字。因此倒序、大队列和多次CPU图像转换必须受限。

相比之下，60秒30 fps、每帧10人、每人17点加框分数按56个float32估算，原始观测数值约4MB；实际对象、索引和序列化另计。默认512维float32特征若保存所有帧所有人，约36.9MB；每人16个特征样本则约0.33MB。缩略图与模型内部激活另计。

700MB可保留为优化预算，不能当作系统统一允许的安全上限。需测进程内存、模型首次加载、解码和GPU相关资源峰值，避免只测Swift堆。有限像素池、背压和及时释放是必须条件。[像素池分配阈值](https://developer.apple.com/documentation/corevideo/kcvpixelbufferpoolallocationthresholdkey)

存储按源片副本、缓存、临时编码与最终文件分别预估。若输出码率假设为10Mbps，60秒视频主体约75MB，音轨和容器另计；源片和导出时临时文件可能同时存在。空间不足时阻止开始或安全失败，不能清理用户源片。

## 画质与运镜评估

1920×1080横屏取满原高度做9:16，裁剪宽度约607.5像素；输出1080×1920需要约1.78倍放大。4K横屏相同取景约1215×2160，可缩小到1080×1920。因此4K解码更贵，却可能提供明显更好的竖屏有效细节。首版可降低分析输入，但导出继续读原片，不能默认以1080p代理替代最终渲染源。

运镜本身处理少量时间序列，预计不是主算力成本，难点是约束。快速横移、画面边缘和全身保护可能要求拉远或补边。仅增加平滑会导致跟随滞后；平滑后逐帧硬截断又会引入抖动。采用前瞻、非对称缩放和约束复核是合理路线，阈值应经实拍播放评审。

单纯位置轨迹没有覆盖快速伸手脚时，需要更密的姿态观测或更宽保护余量。检测与关联可以不同采样率，但必须解释每个关键点来自真实观测还是插值。

## 导出和后台

1080p30裁剪、缩放和编码具有系统实现基础，但硬件编码支持不意味着包含HDR转换、模糊背景和全分辨率读取的整条链路必定实时。先验证纯裁剪，再逐项加入补背景和色彩转换测增量；模糊背景使用低分辨率中间图，避免每帧在完整4K表面上做不必要的重滤镜。

预览与导出共享几何和色彩规则。输出30 fps使用媒体时间采样，保留音轨真实起始偏移。导出P95、HDR样片和音画同步测试独立报告。

iOS 26提供BGContinuedProcessingTask以继续用户在前台发起的工作；支持设备还可申请后台GPU资源，需要能力配置及运行时支持查询。系统仍可排队、取消或结束任务。旧系统和不支持资源的设备采用保存检查点并恢复的路径，不用音频后台模式维持计算。[Apple后台长任务](https://developer.apple.com/documentation/BackgroundTasks/performing-long-running-tasks-on-ios-and-ipados)、[WWDC25说明](https://developer.apple.com/videos/play/wwdc2025/227/)

## 精度目标的可信度

现有98%覆盖、0.5%错误锁定和95%遮挡恢复均是设计目标。人物ReID数据集的排名准确率与本项目的持续身份正确率不同。没有本项目标注测试，不应给出预估达标概率。

0.1次身份切换每目标分钟意味着平均10分钟才有一次；只有几十个事件的初测不足以证明稳定达到此水平。小数据集用于找问题和比方案，扩大样本后报告事件数、目标分钟数、置信区间和各场景分布。

应重点统计身份质量随人物原始高度、检测输入高度、遮挡长度和服装相似度的变化。对长期不可判定区间，允许一次人工锚点纠正具有产品可行性；若每分钟多次纠正，自动跟拍的价值需要重新评估。

## 验证执行与决策门槛

| 顺序 | 验证内容 | 产物与决策 |
| --- | --- | --- |
| 1 | 精确权重导出及输出一致性 | 两个Core ML模型、预处理规范、转换差异报告 |
| 2 | A15和A17 Pro单模型测试 | 冷加载、持续推理P50/P95、算子分配、内存 |
| 3 | 固定观测与特征验证TrackTrack | 移植一致性和应用修改差异 |
| 4 | 代表性舞蹈片段验证身份 | 相似服装、交叉、背身、遮挡的失败清单 |
| 5 | 60秒完整任务 | 所有调用次数、分阶段耗时、重复解码与峰值内存 |
| 6 | 手动框选恢复 | 成功率、额外调用、重算延迟、坐标一致性 |
| 7 | 4K60及10分钟持续处理 | 温升降速、队列峰值、恢复和最坏情况 |
| 8 | 完整竖屏导出 | 有无补背景、HDR转SDR、音画同步及导出耗时 |

性能报告使用Release构建、固定系统与配置，记录实际设备温度状态、电源、低电量模式和后台负载。冷启动、预热和连续运行分别报告，任务耗时包括已提前执行的扫描。至少三次是初测要求，稳定P95需要更多重复任务。UI滚动和播放也测卡顿，不用离线平均吞吐代替交互流畅度。

使用Xcode Core ML性能报告检查算子实际执行设备，结合Instruments与分阶段事件标记检查CPU、GPU、解码和内存。单模型性能报告不包含整个应用的内存和能耗，二者需另外测量。[Apple性能分析](https://developer.apple.com/documentation/coreml/analyzing-a-core-ml-model-s-performance-in-xcode)

保留三类决策：转换或输出严重异常先修复部署；速度不达标先优化处理范围、解码和调度，之后才比较更小Pose模型；身份失败先分析检测缺失、特征不足或关联错误，再决定微调或替换。不能通过降低采样率掩盖交叉错误，也不能通过大量待确认掩盖覆盖率下降。

## 对现有方案的修订建议

1. 将全源逐帧Pose预扫描改成首尾边界搜索和选段分析，保留全程无人时的最坏成本。
2. 明确单次原帧生命周期内尽量完成必要外观提取，二次解码作为有界补充。
3. 为局部重检设置窗口与调用预算，把费用计入任务耗时。
4. 给中间选人与倒序分析单独设性能用例，禁止无界原帧缓存。
5. 相机运动补偿、模型输出形式和TrackTrack参考版本在技术验证前固定。
6. 将60秒、90秒、700MB及身份精度指标标为待测准入目标。
7. 原型保留扫描中、局部恢复中、后台等待或暂停以及不确定身份状态，不展示保证完成时间。

上述为评估建议，原产品与技术方案1.1尚未据此自动改写。原型设计可以继续，模型、身份和全流程三项验证通过后，再冻结开发配置与最低支持机型。
